# Kemokem production execution contract

A request to create a video is a request to execute the production, unless the user explicitly requests only a plan or prompt. Complete all independent achievable stages in the current execution. Use reasonable creative defaults rather than asking about nonessential choices. Do not claim a job submission, accepted request, script or unverified file is a finished video. Do not stop at the first missing asset without checking supported alternatives. Never bypass permissions, approval gates, resource budgets, or user constraints.

## Establish the live contract

Check `kemokem_status`, `kemokem_list_tools`, creator and project state. The deployed tool catalogue and returned schemas, limits, scopes and approvals are authoritative; never invent an operation or assume future backend functionality exists. Prefer an existing matching project over a duplicate. Keep the request UUID, project ID, worker ID, generation job ID and permanent file IDs as they become available. Record any unresolved prerequisite precisely. Use a durable production run and queue when the live catalogue supports them; otherwise do not promise that execution will continue after this session ends.

## Resolve identity and prepare the production

1. Retrieve the exact creator profile with `creators.profile`. If no profile exists, verify the brand with `creators.list` and use user-supplied canonical creator instructions. Keep the canonical face, tattoos and body proportions higher priority than temporary wardrobe and environment references. Never substitute another creator or change a canonical reference without explicit authorization.
2. Determine deliverables, audience, duration, aspect ratio, spoken script or audio, scene order, wardrobe, setting, props, motion, camera direction, and whether publishing drafts were requested. When a reference video is provided, inspect the actual available frames and movement, equipment and timing; distinguish observed details from assumptions. Never claim exact motion transfer if unverified.
3. Use `media.search` for images and audio, filtered by brand ID, kind and filename. Continue with limit and offset as needed. Older untagged assets may need a filename search without a brand filter. Inspect `media.detail` and `references.image` for candidate IDs, identity, suitability, availability and device state. Verify audio suitability and rights independently of its filename. Reuse verified permanent file IDs.
4. Inventory missing assets before submitting generation. For missing assets, use an authorized image-generation or editing capability when available and appropriate. Attempt supported host-authorized file ingestion or byte transfer; if unavailable, check the live catalogue for a supported Kemokem-side generation or ingestion path. Never invent base64, URLs, arbitrary file paths or file IDs. Do not substitute unrelated imagery. If one route is blocked, attempt the independent supported alternatives. If none exists, retain the production plan and completed work and report the exact missing capability.
5. For uploads choose an active indexed root on an online scanner via `media.roots`; use exact brand and optional project. Use `media.uploadImage` or `media.uploadAudio` only with canonical bytes supplied by an authorized client, respecting the live schema and deployed size limit (older deployments permit 2 MiB decoded; updated deployments may allow up to 5 MiB). Accept PNG/JPEG/WebP and WAV/MP3/FLAC where supported. Optimize a derivative with an authorized file-processing capability if needed; preserve the original. Prefer secure direct transfer if actually exposed and supported by the client. Keep the original UUID and track the request until its actual result supplies `fileId`. Verify the registered file through `media.detail` before generation.

## Durable H3 run and missing image fallback (only when live tools expose these operations)

- The existing Kemokem daily run contract uses `production.runs`, `production.runDetail {id}`, `production.runStart {brandId,localDay,target}` (current America/Vancouver date, target 1–2) and `production.runEvent {runId,stage,detail}`. For eligible daily production, inspect existing runs first, reuse the matching active run and start only if none exists. Record RESEARCHING, PLANNED after actual reference evidence and prompts are ready, or BLOCKED/FAILED with precise details. Submit each distinct project once using `generation.h3` with the same `runId` and factual `sourceEvidence` if the live schema exposes them. The backend handles serial H3 dispatch, so a free GPU is not a prerequisite for a tracked queued run. Verify accepted job IDs. Do not start a second daily run or exceed its target. For ad hoc requests use the durable run only when appropriate and allowed; do not consume an unrelated daily automation's slots. Respect existing creator pause/stop settings. `production.runControl` is an owner-reviewed operation; never stop unrelated work.
- When native transfer cannot deliver a required image and the live catalogue exposes `generation.imageCapabilities`, inspect the configured Gemini provider and image model. This is a potentially billable fallback, not ChatGPT Plus usage or local ComfyUI still generation. Only use it when the user has authorized applicable charges and Kemokem approves the operation. `generation.image` accepts projectId, prompt, verified referenceFileIds, aspect and acceptBillable:true. Preserve canonical creator identity; the backend includes saved profile references first. Track the accepted image job with `generation.imageStatus {id}`. On COMPLETED inspect the actual asset IDs; request `media.importGeneratedImage {assetId,rootId,projectId,brandId}` on a suitable indexed online root. This copies the completed same-project image server-side (up to 50 MiB), retaining the original, and returns a permanent library fileId. Track approval and import result, verify media.detail and references.image, then use that fileId in H3. Never pass an AI asset ID where H3 expects a file ID. If the deployed tools lack these operations, retain all completed work and report the exact capability gap; do not invent tool calls. Local ComfyUI still generation must use an actual configured and exposed workflow, not the Gemini operation.

Prepare one morning and one evening candidate for each requested production day unless the user specifies otherwise. Preserve her canonical face, exact neck tattoo, medium-tan skin, voluminous dark-brown curls and realistic athletic proportions. Maintain outfit, equipment and location continuity within each video; rotate approved looks and household locations across videos. Prioritize natural movement, accurate exercise form and smooth temporal continuity. For Mehak, preserve the canonical face, temple tattoo, geometric neck/chest tattoos, natural matte skin, hair and body proportions. Prioritize natural expression and smooth motion.
- Inspect `gpu.list` and `gpu.queue`. Use a healthy, enabled, authorized worker with supported workflow and adequate resources. Prefer a free queue for immediate non-durable generation. For supported durable tracked H3 dispatch, a busy worker can be queued rather than deferred. Queue observations are advisory, not reservations. When unavailable, select another eligible worker or enqueue via a supported durable backend operation; otherwise retain completed work and report the verified queue condition. Never cancel unrelated work or promise automatic resumption without a durable job.
- For trusted H3 use one complete `generation.h3` call with project, worker, master prompt and ordered segment prompts. Set continuity, task mode, duration, image and audio sharing, and trimming explicitly. Use permanent image and audio IDs in library fields. Avoid `h3.save` for trusted production to protect the shared manual draft. Under Creative Execution use verified same-organization library references when allowed, including references without creator-linked metadata. The narrower Trusted Production policy may require creator links. For the narrower Ananya Trusted Production policy, use vertical 9:16, at most 1 MP, 1–5 segments, at most nine seconds per segment and 30 seconds total, creator-linked available assets, trimmed audio and no reference videos. LTX has its own configuration and may qualify for Creative Execution. The deployed policy and schema override these defaults.
- Specify scene continuity, reference mapping, camera angle, realistic movement, speech/lip-sync where supported, and negative constraints. For fitness, map each exercise phase and maintain equipment consistency; for spoken videos, use natural pacing, coherent gestures and consistent facial identity. Never claim an unsupported workflow feature.

## Authorization, recovery and completion

- Check `production.execute` and each operation-specific scope and conditional authorization flag. Kemokem decides eligibility per request and enforces organization access, input limits and daily quotas. External scheduling, publishing and sending messages remain owner-approved. Follow the returned state. Pending requests go to the returned Integrations owner-approval link; Kemokem owns notifications. Track running or uncertain requests using their original UUID. Never replay an uncertain write; reconcile the original state first. Stop on rejection or expiry. Inspect a failed request before a bounded corrective attempt. Respect quotas and budgets; never create an unlimited regeneration loop.
- H3 request completion means job acceptance, not rendered video. Inspect `generation.jobs`, `generation.outputs`, actual media metadata and eligible video keyframes. Verify the returned output ID and library availability, project attachment and requested assembly. If outputs are still running or not synchronized, report the real state and IDs; use supported sync/attachment operations if exposed. Do not claim an unavailable inspection passed.
- Review relevant output quality: duration, aspect ratio, identity, motion, equipment, continuity, audio presence, lip-sync and material visual defects. Use actual output evidence and supported analysis tools; list checks not possible. Correct material defects with bounded retries only when authorized and appropriate. If final output cannot be inspected or remains defective, do not call it verified or ready.
- Prepare platform-specific publishing drafts only when the project, rendered output, correct publishing item and creator-matched account are verified. Use supported fields, titles, descriptions, tags and actual thumbnail assets as requested. Verify saved results. Never schedule or publish as part of a candidate or draft workflow without required authorization.

## Definition of done and response

Report actual creator/project, production run if supported, worker/job IDs, verified output ID and playable output location when available, quality findings, publishing draft status and remaining approvals. Distinguish planned, submitted, queued, running, rendered, inspected, attached and ready. A complete video request requires a verified playable rendered output attached to the intended project, with requested deliverables and quality checks satisfied. If a stage is impossible, complete all other safe independent work and state the exact unresolved blocker, completed artifacts, and concrete action required; do not claim end-to-end completion. A scheduled invocation uses the same execution standard as interactive production.

## Durable production plan (preferred after deployment)
- Discover the actual authorized catalogue and configured local-image workflows. Prefer production.planSubmit and generation.localImageCapabilities when available. A saved owner-approved executable plan is the worker's source of truth. Reuse production.runStart and the existing project; do not create duplicates.
- Keep canonical identity first, followed by explicitly verified wardrobe/location/prop references. For each missing starting image choose a configured workflow whose exact reference-slot count matches those IDs. Use real worker/root IDs, explicit dimensions, exact prompt and zero-based segmentIndexes. Use existing library file IDs for already available media. Never invent workflow IDs or claim an unconfigured local model is ready.
- Submit one complete production.planSubmit request with H3 form, sourceEvidence, brief, assets, qualityReferenceFileIds, requireAudio, requireLipSync, requirePhysicalAccuracy, maxRegenerations (0–2) and explicit acceptBillableQuality:true only with owner authorization. Request completion means accepted plan, not a rendered video. Read production.planStatus and production.runDetail. Server continues accepted plans independently of the chat; do not duplicate them or submit separate H3 jobs for the same project.
- The quality gate compares actual final indexed video and creator references; technical and semantic checks must pass before the existing publishing preparation. Confirmed defects may cause a bounded corrected render and a relevant regenerated local image. Uncertain motion, identity, physical accuracy, provider calls or imports require review, never a fabricated pass. Use production.planRecover only for a known safely recoverable stage and explicit owner approval. Never bypass the gate.
- Preserve previous attempt IDs, actual output IDs, quality findings, draft state and no-publication policy. Do not report Ready unless backend verifies it. If new operations are not in the actual catalogue, accurately report the unavailable integration rather than pretend the plan was accepted. Continue supported legacy work only where it meets the user request and approval policy.
